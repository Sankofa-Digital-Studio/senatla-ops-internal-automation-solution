# Site Manager Phase 2 Findings and Delivery

**Review date:** 18 November 2026  
**Scope:** Phase 1 three-pass review and implemented Phase 2 governance foundation

## Executive finding

Phase 1 improved operational continuity, but its manager overlay was browser-local. It could not serve as a shared, reliable handover record, and a UI-only readiness check could be bypassed by a direct database write. Phase 2 now provides a server-backed, site-scoped control record with database-enforced start gates, atomic versioned saves, role-limited handover review, and database-generated audit events.

This is a substantial Phase 2 foundation, not completion of every planned Phase 2 domain. Competence, toolbox talks, full permits, quality/NCR, material readiness, and cross-role escalation remain open backlog items.

## Three-pass Phase 1 analysis

### Pass 1 — Evidence from the delivered behavior

- The manager overlay already covered shift intention, risk, support, handover, workshop work packages, readiness checks, attendance warnings, and manually managed blockers.
- Its persistence was in browser storage, scoped by site and date.
- The interface explicitly did not claim local persistence was server audit evidence.
- Operational data was not yet shared reliably between managers and devices.

### Pass 2 — Challenge assumptions and failure paths

| Finding | Operational impact | Priority |
| --- | --- | --- |
| Browser-local state is not a shared handover record | A second manager/device can miss or lose the plan | Critical |
| Start checks exist in the UI only | Direct writes could bypass readiness and attendance checks | Critical |
| Work date was conflated with package due date | Readiness and attendance could be evaluated against the wrong day | High |
| Client-supplied audit rows are forgeable | The event trail cannot be trusted as evidence | Critical |
| Parent and child records save separately | A failure can leave a partial control record | High |
| Concurrent edits lack conflict control | A stale manager view can overwrite newer work | High |
| Review permissions can become broad edit permissions | Maker-checker separation is weakened | High |
| New operational modules risk duplicating existing systems | Conflicting sources of truth and workflow drift | High |

### Pass 3 — Decisions, improvements, and trade-offs

The Phase 1 weaknesses drove the Phase 2 foundation: a shared Supabase gateway; RLS-protected manager tables; distinct work-date and due-date fields; readiness and attendance enforcement in database paths; trigger-generated append-only audit events; reviewer-only handover status changes; and atomic saves with idempotency and optimistic version checks.

The chosen boundary is an execution overlay that reads existing attendance and site authority sources. It does not establish parallel procurement, attendance, or safety systems. The next Phase 2 work should extend this governed record with explicit competence, permit, quality, material, briefing, and escalation workflows.

## Implemented in this slice

- Server-backed manager snapshots, workstation readiness, blockers, work packages, and event audit records.
- Site/date authorization through row-level security.
- Atomic multi-record saves with retry idempotency and stale-version rejection.
- Server-side `in_progress` gate: six readiness checks plus an assigned person recorded present.
- Append-only audit events generated by database triggers; authenticated clients cannot directly write or delete them.
- Reviewer status workflow with restricted reviewer authority and accepted-handover immutability.
- Separate work date from package due date.
- Foreign-key indexes and auth-policy tuning applied to the connected database.
- Local fallback gateway and UI save queue for review and offline-like local mode.

## Verification and limits

- Remote pgTAP database contract: **33 assertions passed**, including authenticated save, idempotent replay, and stale-version rejection.
- `npm run typecheck`: passed.
- `npm run lint`: passed.
- `npm run build`: passed before the final template copy update; rerun in final verification.
- Focused Angular specs compiled, but the ChromeHeadless runner did not complete in this environment. Do not treat that as a passing browser test.
- Full local Supabase test suite was unavailable because Docker is not installed. Remote contract execution was used for database verification.
- Supabase advisors showed no new Phase 2 foreign-key or auth-initplan findings after index/policy tuning. Unrelated pre-existing security findings remain outside this change.
