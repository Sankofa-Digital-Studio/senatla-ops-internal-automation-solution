# Senatla Ops v0.5.4 release and support guide

**Document status:** Release candidate guide · **Updated:** 7 November 2026 · **Audience:** release owner, operations support, QA, and Director reviewers

This guide explains the v0.5.4 public landing, analytics, Director, verification, and recovery workflows. The application was promoted through `preview` to `main` in PR #114; the canonical Vercel project reports a successful production deployment for commit `53fb4aac1f1e424bfd795b7286ec0384c4947daf`. Authenticated hosted smoke, backup restore, and rollback rehearsal are still pending. Promotion alone does not close those acceptance checks.

## 1. Release decision at a glance

**Current decision: production deployed; acceptance pending evidence.** The successful Vercel deployment URL is <https://senatla-g2ca7vkls-ohhttooexcivs-projects.vercel.app>. Protected preview smoke run [42413699671](https://github.com/Sankofa-Digital-Studio/senatla-ops-internal-automation-solution/actions/runs/42413699671) failed before browser tests because the bypass request followed repeated redirects. Use an authorized test account; keep credentials, tokens, private records, and screenshots of sensitive data out of the release packet.

The public canonical page is **<https://senatla-ops.vercel.app/landing>**. Only `/landing` is intended to be indexable. The root route, login and registration, protected workspaces, and unknown SPA routes are intended to receive `noindex, nofollow, noarchive` through response headers and route metadata. The sitemap lists only `/landing`; `robots.txt` allows crawlers to see noindex directives. Preview pages retain the production canonical URL. If the public domain changes, update the committed HTML, sitemap, and configured origin together in a reviewed release. See the [route indexing matrix](seo-indexing-matrix.md).

The Director workspace guidance and proposal template guides already exist in Markdown, responsive HTML, and Word form. The repository describes seven proposal formats and a builder with spreadsheet preview, Excel export, and draft PDF export. Treat hosted availability and export behavior as unverified until the authenticated smoke below is recorded. Historical workbooks supply layout patterns, not trusted prices or asset data. See [Director workspace guidance](director-workspace-guidance.md) and [proposal templates](director-proposal-templates.md).

## 2. Public landing and analytics workflow

### 2.1 Public visitor path

1. Open `/landing` on desktop and narrow mobile screens. Confirm the page is readable, the sign-in and APK actions are reachable, and no horizontal overflow obscures controls.
2. Inspect the served page and response: canonical URL is the approved `/landing` address, landing metadata permits indexing, and the sitemap contains only this route.
3. Inspect `/`, `/login`, `/register`, `/director`, and a nonexistent path. Confirm their response headers and client metadata prevent indexing. Do not infer server headers from the page DOM alone.

### 2.2 Consent and event path

Optional GA4 analytics is configured only through a valid `SENATLA_GA4_MEASUREMENT_ID` (`G-…`) in the approved Vercel environment. **A blank ID disables both the GA4 script and the consent prompt.** With a valid ID, the landing page offers **Accept** and **Decline**; the choice is stored locally under a versioned key and can be changed from **Analytics choices** in the footer. No analytics script should load before acceptance. Confirm keyboard access and touch targets on iOS Safari and Android Chrome.

The application emits only `landing_view`, `sign_in_click`, and `apk_download`, from the public landing page, without identity, amounts, operational records, or arbitrary event payloads. Protected workspaces do not emit application analytics events. GA4 can create automatic events after consent; review its property settings and live stream before enabling a production ID. Do not place an API secret or service-role credential in browser runtime configuration. Import only actual aggregate counts into the existing [GA4 workbook instructions](analytics-workbook-v0.5.4.md). See [analytics privacy](analytics-privacy-v0.5.4.md).

## 3. Authenticated support workflow

### 3.1 Sign-in and Director guidance

Use an authorized account for the intended role. On first Director entry, verify the guided walkthrough reaches each target and can be replayed from **Help**. Confirm the final per-user preference, ordinary Director oversight, and the restricted developer Director administration boundary described in the [workspace guidance](director-workspace-guidance.md). Capture results without exposing account credentials or private operational records.

If login fails, record the visible support reference, time, route, role, environment, and browser. If sign-out takes too long, wait for the visible retry state and retry once. Escalate a repeated failure with the reference and deployment ID. Do not interpret a spinner as a successful authentication or sign-out result.

### 3.2 Proposal template review

Open **Proposal templates** as an authorized Director. Check the seven documented formats, editable sections and items, zero or blank starting financial inputs, live calculation, spreadsheet preview, Excel formulas, and draft PDF download. Verify that unpriced lines remain visible and exports disclose their count. Check client and contract-party text with a human before external issue. The builder does not save a draft to the database; preserve a downloaded file under the approved document process if needed. No archived rates, personnel, or assets should appear as prefilled data.

## 5. Promotion and rollback workflow

### 5.1 Before promotion

1. Confirm the exact candidate commit and reviewed `dev` → `preview` → `main` path. Record the Vercel deployment that contains that commit.
2. Attach `npm run verify` results, database migration and role-contract results if applicable, hosted smoke, responsive and device results, and business acceptance. Resolve failed checks or record an explicit release decision with the remaining risk.
3. Record the known-good deployment ID, configuration version, database migration state, backup reference, restore rehearsal result, rollback owner, and communication route. Keep secrets out of the packet.
4. Obtain Engineering, Operations, and Finance acceptance required by the [production candidate checklist](release-checklist.md). Only then record an authorized promotion and verify the production deployment separately.

### 5.2 If the candidate fails after promotion

Stop further changes and preserve the failing deployment ID, time, symptom, impact, and logs. The release owner selects the recorded known-good Vercel deployment and executes the approved rollback procedure. Check database compatibility before reverting application code; a deployment rollback alone may not reverse a migration or data change. Restore data only under the rehearsed, approved recovery plan. Re-run public landing, noindex, sign-in, core Director, and analytics-disabled smoke on the restored deployment. Record who acted, the exact target, outcome, residual risk, and stakeholder notice. Escalate if the target or compatibility cannot be verified.

**Rollback evidence is pending.** This section is a procedure and evidence requirement; it does not claim a rollback was rehearsed or executed for v0.5.4.

## 6. Troubleshooting and escalation

### Landing or indexing is wrong

Compare the deployed commit and runtime canonical origin with the served HTML, sitemap, robots file, response headers, and client route metadata. A browser-rendered meta tag alone does not prove the server response. Keep the incident open until the hosted result is captured.

### Analytics appears before consent or while the ID is blank

Stop analytics enablement. Check the deployed runtime ID, consent storage state, network requests, and GA4 property settings. Re-test a clean browser profile and both Accept and Decline paths. Do not use a service credential to diagnose public analytics.

### Director access or templates differ from the guide

Confirm deployment identity and authorized role first. Reproduce with a safe test record and note the exact format or action. Check whether the change is only in `dev` or documentation and whether `preview` contains the expected commit. Escalate missing export, formula mismatch, prefilled historical values, or role elevation before acceptance.

### Sign-in, sign-out, or mobile use fails

Capture the support reference, time, device, browser version, route, and deployment. Retry only where the UI offers it. For mobile layout, note the viewport, orientation, keyboard state, and control that fails. Do not ask users to send passwords, tokens, or private records.

## 7. Acceptance record

The release owner records **Accepted**, **Rejected**, or **Deferred** with date and evidence links. Acceptance requires the hosted smoke rows above, no unresolved critical privacy or role-access defect, a known-good rollback target with compatible data state, restore and rollback evidence, and named Engineering, Operations, and Finance approvals. Any missing item remains **Pending evidence**. A pass for a local test or one browser cannot stand in for hosted or device evidence.
